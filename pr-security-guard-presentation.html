Hardcoded Secrets
Developers accidentally paste real API keys, passwords, and database credentials directly into source code during rapid development.

A single hardcoded key committed to a public fork stays valid until someone manually rotates it — often days later. Attackers scan public repos for exactly this pattern within minutes of a push.

💉
SQL Injection
A developer takes a shortcut and builds a database query by pasting user input directly into it — letting attackers manipulate the query.
"SELECT * FROM accounts WHERE id = " + userId;
// Should be: preparedStatement with ?

This exact shape of bug is invisible in code review 90% of the time — it looks like ordinary string building. It only reveals itself under a crafted input, by which point it's usually already in production.

Low Level Design (LLD)
The Agent Pipeline — One Request, Start to Finish
Five sequential stages. Follow one real PR — a hardcoded API key + a SQL injection in server.js — as it moves through each one
00Webhook Received
▸ ARRIVES AS
POST /webhook/github X-Hub-Signature-256: sha256=... { "action": "opened", "pull_request": { "number": 3, ... }, "repository": { "full_name": "user/payment-service" } }
→
▸ LEAVES AS
diff_content: "diff --git a/server.js..." package_json_content: "{ full file }" pr_title, pr_author, head_sha
What happens: Spring Boot validates the HMAC signature to confirm this really came from GitHub, then DiffExtractorService fetches the full unified diff and — since package.json appears in it — also fetches its complete file content so CVE scanning isn't limited to just the new lines.
01Regex Prefilter
▸ ARRIVES AS
diff_content — every + added line, e.g.: +const API_KEY = "sk-live-xK9..." +db.query("SELECT * WHERE id=" + id)
→
▸ LEAVES AS
prefilter_hits: [ {type: "HARDCODED_API_KEY", line: 14}, {type: "SQL_INJECTION", line: 19} ]
What happens: No AI call yet — every added line runs against compiled regex patterns for secrets and dangerous calls. This is instant, free, and deterministic: the same input always produces the same hit. These hits become a safety net later — if the AI pipeline ever drops one of these, the gate re-injects it.
02CVE Scanner
▸ ARRIVES AS
package_json_content (full file) "dependencies": { "express": "4.17.1", ... }
→
▸ LEAVES AS
cve_findings: [ {dep: "express:4.17.1", cve_id: "CVE-2022-24999", cvss: 7.5} ]
What happens: Every dependency is extracted and batch-queried against Google's OSV database — a real vulnerability lookup, not the LLM guessing from training data. This runs in parallel conceptually with regex; both feed into the next stage as context.
03LLM Analyzer
▸ ARRIVES AS
diff_content + prefilter_hits (2) + cve_findings (1) → sent to Mistral Codestral
→
▸ LEAVES AS
raw_findings: [ {type:"HARDCODED_API_KEY",conf:0.95}, {type:"SQL_INJECTION",conf:0.85}, {type:"XSS_RISK",conf:0.62} ]
What happens: Mistral reads the diff plus the regex/CVE context and returns structured JSON findings with its own confidence scores. Line numbers get corrected against the precise regex data, and any regex hit the LLM missed gets merged back in here — so the LLM can add findings, but it can't make the deterministic ones disappear.
04Self-Reflection
▸ ARRIVES AS
raw_findings (3) → sent back to Mistral as a second, separate call: "critique your own findings"
→
▸ LEAVES AS
critiqued_findings: [ {..., verdict:"CONFIRMED", final_conf:0.97}, {..., verdict:"CONFIRMED", final_conf:0.89}, {..., verdict:"FALSE_POSITIVE", final_conf:0.30} ]
What happens: A second AI call second-guesses the first one — asking whether each finding could be a test file, an env-var reference, or already sanitized. Confidence shifts up or down per finding. The XSS finding here got demoted to a likely false positive.
05Gate Decision
▸ ARRIVES AS
critiqued_findings (3) + prefilter_hits (2) — used as a safety-net cross-check
→
▸ LEAVES AS
gate_decision: "BLOCK" block=2 warn=0 discard=1 → posted to GitHub PR → written to PostgreSQL
What happens: Thresholds apply — CRITICAL/HIGH findings above 0.85 confidence block the merge. The confidence floor also rescues any high-confidence finding critique wrongly dismissed. The final decision, every finding, and the LangSmith trace ID are written to Postgres, and the summary table is posted back to the PR — the report you actually see on GitHub.

The Clever Part
Self-Reflection Loop
The AI second-guesses itself before blocking anyone's PR — the key to enterprise trust
01
Initial Finding
Mistral Codestral reads the diff and produces raw findings: type, location, severity, initial confidence score.
02
Adversarial Critique
A second AI call asks: "Is this actually in a test file? Is this an env variable reference? Could this already be sanitized upstream?"
03
Confidence Adjustment
Each finding gets a confidence score adjustment (−0.40 to +0.15). False positives are identified and discarded.
04
Threshold Gate
Only findings with final confidence ≥ 0.85 block the merge. Between 0.60–0.85 → warning. A confidence floor also rescues high-confidence findings the critique wrongly dismissed, so nothing vanishes silently.

Dependency Security
CVE Detection Engine
Real vulnerability database lookups — not AI guessing from memory
Step 1 — Fetch full pom.xml
When pom.xml appears in a PR, we fetch the COMPLETE file from GitHub (not just the diff). This catches pre-existing vulnerable dependencies, not just newly added ones.
Step 2 — Extract all dependencies
Parse every <dependency> block in the full pom.xml. Resolve property references like ${log4j2.version} back to real version numbers. Produces a list of groupId:artifactId:version tuples.
Step 3 — Query OSV database
Batch-query api.osv.dev for all dependencies at once. For each vulnerability ID found, fetch full details including CVSS score, CVE alias, and remediation link. Free, no API key, covers 50k+ packages.
